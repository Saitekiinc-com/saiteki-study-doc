# 書籍購入補助制度 利用者向けドキュメント更新計画

## 目的

書籍購入補助制度の現状手順で、利用者が「次に何をすればよいか」「どの時点で申請が完了するのか」「つまづいた時に何を確認すればよいか」を判断できるようにする。

今回の計画では、GitHub Issue テンプレート、GitHub Actions、自動ラベル同期、承認・精算フローの実装は変更しない。まずは利用者向けドキュメントだけを更新し、既存運用への影響を最小にする。

## 背景

現状の公開ドキュメントには、制度ルールと大まかな手順はあるが、実際の利用者が迷いやすい補足が不足している。

- AI推薦用の Issue 作成と、購入補助申請が同じ入口になっている
- 購入する本を決めた後に、どこまで対応すればよいかが分かりにくい
- チェックボックスをいつ、誰が入れるのかが分かりにくい
- 領収書添付時に確認される情報が分かりにくい
- 書籍レポート作成時に、親の購入申請 Issue とどう紐づけるかが分かりにくい
- 申請者、上長、自動処理の待ち状態が見えにくい

## 方針

短期対応として、現在のフローを変えずに「迷いを減らす説明」を足す。

- 手順は、申請者が実際に行う順番で書く
- 「誰が」「どこで」「何を書くか」を明記する
- 領収書添付コメントは必要な手順として明記する
- 購入候補コメントや推薦外書籍の選定理由コメントなど、現行運用で必須ではないコメントを必須のように見せない
- 申請完了、承認待ち、レポート待ちなどの状態を言葉で説明する
- 実装されていない自動化を、実装済みのように書かない
- 中長期の理想フローとは分けて、現時点で動く運用だけを案内する

## 対象ファイル

### 更新対象

- `docs/knowledge_base/index.md`
  - 制度概要と重要ルールを整理する
  - 「まず何を読めばよいか」を明確にする

- `docs/knowledge_base/purchase_flow.md`
  - 購入補助ありの手順を、利用者目線で詳しくする
  - チェックボックス操作、待ち状態、FAQを追加する
  - 購入補助なしのレポート投稿との違いを明確にする

- `docs/knowledge_base/issue_book_search.md`
  - AI推薦 Issue が購入補助申請の入口であることを明記する
  - 推薦後に利用者がどこまで対応すればよいかを補足する

- `docs/knowledge_base/issue_book_report.md`
  - 購入補助を受けている場合のレポート作成方法を補足する
  - 親 Issue から作る理由と、PR作成後に何が起きるかを説明する

### 今回は更新しない対象

- `.github/ISSUE_TEMPLATE/*.yml`
- `.github/workflows/*.yml`
- `scripts/**/*.ts`
- ラベル定義、チェックボックス同期、自動バリデーション
- 経理・精算の実装フロー

## 最終ページ構成

利用者が読む順番は、`index.md` から `purchase_flow.md` に進み、必要に応じて個別手順ページを見る構成にする。

### ページ役割

| ページ | 役割 | 主な読者 |
|---|---|---|
| `index.md` | 制度の入口。対象者、ルール、読むべき手順への導線を置く | 初めて制度を使う人 |
| `purchase_flow.md` | 購入補助あり/なしの全体フロー。実際に何をすればよいかをまとめる中心ページ | 申請者、上長 |
| `issue_book_search.md` | AIによる書籍選定 Issue の作成手順。Issue作成画面で迷った人向け | 申請者 |
| `issue_book_report.md` | 書籍レポート Issue の作成手順。読了後に迷った人向け | 申請者、レビューする上長 |
| `issue_close.md` | 間違えて Issue を作った、取り下げたい場合の補助ページ | 申請者 |

### `index.md` の構成

1. 書籍購入補助制度の概要
2. 制度の決まり事
   - 対象者
   - 月1回まで
   - 対象書籍
   - 5000円上限
   - 購入月の月末までに申請
   - 領収書添付
   - 読了後の書籍レポート作成
3. GitHubアカウントについて
4. 初めて使う人への案内
   - 購入補助を受ける場合は `purchase_flow.md` へ
   - レポートだけ投稿する場合も `purchase_flow.md` へ
5. 関連ガイドリンク

### `purchase_flow.md` の構成

1. このページで分かること
2. 購入補助を受ける場合の全体像
3. 申請者が行う手順
   - GitHubアカウントを準備する
   - AIによる書籍選定 Issue を作る
   - AI推薦を確認する
   - 購入する本を決める
   - 商品リンク添付チェックを入れる
   - 本を購入する
   - 領収書を Issue コメントに添付する
   - 領収書添付チェックを入れる
   - 上長の承認を待つ
   - 読了後に書籍レポート Issue を作る
   - PR作成、レビュー、公開を待つ
4. 上長が行う手順
   - 領収書と制度条件を確認する
   - `承認済み (上長)` にチェックを入れる
   - 書籍レポートPRを確認する
5. チェックボックスの意味
   - 申請者が入れるもの
   - 上長が入れるもの
6. 領収書添付時の確認ポイント
7. 購入補助なしで書籍レポートだけ投稿する場合
8. よくあるつまずき
9. 関連ページ

### `issue_book_search.md` の構成

1. AIによる書籍選定 Issue の位置づけ
   - 購入補助申請の入口であること
   - AI推薦は参考であること
2. Issue作成ページを開く
3. フォームに入力する
4. Issueを送信する
5. 推薦後に行うこと
   - 購入する本を決める
   - 必要なチェックボックスがあることを確認する
   - 詳細な流れは `purchase_flow.md` を見る

### `issue_book_report.md` の構成

1. 書籍レポートの位置づけ
2. 購入補助を受けている場合の作成方法
   - 元の購入申請 Issue から作る
   - 親 Issue との紐づけを保つ
3. 購入補助なしの場合の作成方法
4. フォーム入力項目
5. Issue送信後に起きること
   - PRが自動作成される
   - 上長レビュー後に公開される
6. PR確認・マージの流れ

### 情報配置のルール

- 制度ルールは `index.md` に置き、詳細手順は `purchase_flow.md` に置く
- `issue_book_search.md` と `issue_book_report.md` は、Issue作成画面で迷った時の補助ページにする
- FAQは `purchase_flow.md` に集約する
- 同じ説明を複数ページに重複させすぎず、詳しい説明は `purchase_flow.md` へリンクする
- 現行フローで不要な購入候補コメントや推薦外書籍の選定理由コメントを、必須手順として書かない
- 領収書を Issue コメントに添付する手順は、必要な手順として `purchase_flow.md` に明記する

## 追加する内容案

### 1. 最初に読むページの整理

`index.md` には、制度ルールの下に次の導線を追加する。

- 初めて使う人は `書籍購入・レポート投稿フロー` を読む
- 申請は GitHub Issue で行う
- AI推薦は参考であり、推薦外の書籍も購入できる
- 領収書を出しただけでは完了ではなく、上長確認と読了後レポートが必要

### 2. 申請者向けの詳細手順

`purchase_flow.md` の購入補助ありフローを、次の単位で整理する。

1. GitHub アカウントを準備する
2. AIによる書籍選定 Issue を作る
3. AI推薦を確認する
4. 購入する本を決める
5. 商品リンク添付チェックを入れる
6. 本を購入する
7. 領収書をコメントに添付する
8. 領収書添付チェックを入れる
9. 上長の承認を待つ
10. 読了後に書籍レポート Issue を作る
11. PR作成・レビュー・公開を待つ

### 3. 領収書添付時の確認ポイント

領収書添付時に利用者が迷わないよう、コメントの定型文ではなく確認ポイントを追加する。

- 領収書は画像添付でよい
- 購入日、購入金額、購入先が分かる状態にする
- 領収書は Issue コメントに添付する
- コメント本文の書式は固定しないが、領収書添付コメント自体は必要
- 領収書を添付した後に、`領収書を添付した (申請者)` にチェックを入れる

### 4. チェックボックスの説明

現在の Issue には、自動で次のチェックボックスが追加される前提で説明する。

- `購入したい書籍の商品リンクを添付した（申請者）`
- `領収書を添付した (申請者)`
- `承認済み (上長)`

説明では、申請者が入れるものと上長が入れるものを分ける。

- 申請者が入れる
  - 商品リンク添付
  - 領収書添付
- 上長が入れる
  - 承認済み

### 5. よくあるつまずき

FAQとして、次の内容を追加する。

- AI推薦以外の本でもよいか
- 領収書は画像でよいか
- 商品リンクと領収書は同じタイミングで添付してよいか
- 申請後に本を変えたい場合はどうするか
- 書籍レポートはいつ作るか
- 間違えて Issue を作った場合はどうするか
- PRが作られない場合はどうするか
- 購入候補や推薦外書籍の選定理由を毎回コメントする必要があるか
- 領収書はどのコメントに添付すればよいか

## 影響範囲

今回の更新は Markdown ドキュメントのみのため、既存利用者の操作、GitHub Actions、自動ラベル、Issue テンプレート、承認・精算処理には影響しない。

公開サイトに反映された後、ドキュメントを見た利用者の行動は変わる可能性がある。ただし、これは既存フローを分かりやすく案内する変更であり、制度条件や申請方法そのものを変えるものではない。

## リスク

- 実装されていない理想フローを書いてしまうと、利用者が期待と違う挙動に戸惑う
- 詳細を書きすぎると、かえって読む量が増える
- 経理・承認の正式運用が未確定の場合、断定表現が誤解を生む

## リスクへの対応

- 「現時点の手順」と「今後改善したいフロー」を混ぜない
- 利用者向けページでは、実際に操作する内容だけを書く
- 経理・承認に関する表現は、上長確認を待つ、承認後に翌月給与と一緒に振り込まれる、という既存ルールの範囲に留める
- 詳細な運用設計は `mvp_workflow_policy.md` などの内部向け文書に分ける

## 完了条件

- 初めて利用する人が、購入補助申請から書籍レポート提出までの流れを追える
- 申請者が領収書添付時に何を確認すればよいか分かる
- 申請者がどのチェックボックスを入れるべきか分かる
- 上長がどのチェックボックスを入れるべきか分かる
- AI推薦外の書籍でも購入できることが分かる
- 領収書添付後、何を待てばよいか分かる
- ドキュメントビルドが成功する

## 作業ロール案

今回の更新は小さく、必ずしもサブエージェント分担は必要ない。分担する場合は、次の役割に分ける。

| ロール | 担当範囲 | 成果物 |
|---|---|---|
| 利用者目線レビュー | 初めて申請する人が迷う箇所を洗い出す | FAQ項目、手順の不足指摘 |
| ドキュメント編集 | `purchase_flow.md`、`issue_book_search.md`、`issue_book_report.md`、`index.md` を更新する | Markdown更新 |
| 運用整合性レビュー | 領収書添付コメントなど必要な手順を残しつつ、不要なコメント運用を必須に見せていないか確認する | 修正指摘 |
| 技術確認 | VitePressビルド、リンク、表示崩れを確認する | `npm run docs:build` の結果 |

## 実施順序

1. `purchase_flow.md` を中心に、利用者向けの詳細手順、チェックボックス説明、FAQを追加する
2. `issue_book_search.md` に、推薦後の購入申請アクションを追記する
3. `issue_book_report.md` に、購入補助ありの場合の親 Issue 紐づけを補足する
4. `index.md` の導線を整理する
5. `npm run docs:build` で表示崩れやリンク切れがないか確認する

## 次の判断ポイント

ドキュメント更新後も同じつまずきが残る場合は、フロー改修を検討する。

- 購入申請 Issue テンプレートに対象月、金額、購入予定書籍、領収書欄を追加する
- チェックボックスとラベル同期の対象を増やす
- 不足情報がある場合に自動コメントで案内する
- レポート未提出者の次回申請ブロックを自動化する
